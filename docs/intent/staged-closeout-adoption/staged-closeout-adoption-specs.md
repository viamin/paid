# EARS Specs: Staged Closeout Adoption

- [x] **STAGED-CLOSEOUT-ADOPTION-006** — When an authorized maintainer opens project acceptance-check settings, Paid SHALL provide HTML controls to inspect and change enrollment, review or replace a mapping using current criteria and permitted registry targets, revoke a mapping, and inspect revision history with reviewer identity, time and eligibility reasons; equivalent JSON actions SHALL remain available.
  *Test:* `spec/requests/projects/staged_closeout_adoptions_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-007** — When a reviewed mapping is changed or admitted, Paid SHALL reject in-place changes to its reviewed inputs and reject admission for a different source issue, project, account or enrollment.
  *Test:* `spec/services/staged_closeout_adoption/mappings_eligibility_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-001** — When a project has no staged-closeout enrollment, it SHALL be disabled, regardless of auto-merge or auto-pick settings.
  *Test:* `spec/services/staged_closeout_adoption/enroll_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-002** — When an authorized maintainer enables, disables, approves, changes, or revokes staged-closeout adoption, Paid SHALL persist the actor and time and retain superseded mapping history.
  *Test:* `spec/services/staged_closeout_adoption/mappings_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-003** — When a mapping is reviewed, Paid SHALL accept only a current stable criterion, permitted registry target with pinned version and digest, matching stage/phase, and project/account scope; untrusted proposals SHALL not approve it.
  *Test:* `spec/services/staged_closeout_adoption/mappings_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-004** — When an enrollment is disabled, a mapping is replaced or revoked, or its target changes, mapping admission SHALL reject it with an inspectable reason while retaining history.
  *Test:* `spec/services/staged_closeout_adoption/mappings_eligibility_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-005** — When a project or account with reviewed staged-closeout mappings is deleted, Paid SHALL delete its mappings, source issues, enrollment, and owning tenant records without a dependency-order failure.
  *Test:* `spec/models/project_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-008** — When the curated Fully Automatic (`solo_automated`) profile is planned or (re)applied, Paid SHALL treat staged-closeout enrollment as an explicit profile target — enabled by Fully Automatic and explicitly off for every other curated profile — persist the enrollment through the authorized profile workflow with reviewer identity and revision history, serialize concurrent first enrollment creation, restore the prior value on profile rollback, and skip and report only the enrollment target when the caller lacks project-update authority so other profile targets still apply. Paid SHALL NOT enable a deployment executor, Operations remediation, or bypass a disabled phase or missing required authorization; absent an approved mapping or available target the project SHALL receive an inspectable waiting reason.
  *Test:* `spec/services/configuration/profiles/solo_automated_staged_enrollment_spec.rb`, `spec/services/staged_closeout_adoption/enrollment_target_spec.rb`, `spec/services/automation/effective_policy_staged_verification_spec.rb`, `spec/services/configuration_profiles/applier_staged_enrollment_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-009** — When Paid authoritatively observes a source PR merge for an enabled project, it SHALL admit one queued synthetic `closeout_verification` run for every eligible current `merged_revision` mapping, pinning project, source issue, criterion, source PR, observed merged SHA, recipe version, and recipe digest; it SHALL not dispatch that run through ordinary agent execution.
  *Test:* `spec/services/closeout_verifications/admit_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-010** — When the same merge is observed by Paid auto-merge, a GitHub webhook, concurrent delivery, or a bounded reconciliation sweep, Paid SHALL converge to the same run identity; an invalid mapping, unavailable authority, pause, absent lineage, current result, or unconfirmed live target SHALL produce an inspectable no-run reason. The admission row and its execution job SHALL persist atomically, so a failed job enqueue SHALL NOT strand a queued identity against re-observation.
  *Test:* `spec/services/closeout_verifications/admit_spec.rb`, `spec/requests/api/github_webhooks_spec.rb`, `spec/jobs/closeout_verification_reconciliation_sweep_job_spec.rb`, `spec/temporal/activities/fetch_issues_activity_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-011** — When an admitted merged-revision `closeout_verification` run is claimed, Paid SHALL recheck its reviewed mapping, pinned merged target, automatic release policy, pause state, and budget before executing only the reviewed recipe through `TechnicalPrerequisites::ValidateExecution` in its isolated environment. It SHALL defer the queued identity when pause, hard-stop budget, assessment staleness, or an unexpected pre-execution exception is recoverable through re-observation, while pinned-target divergence, policy revocation, mapping or recipe mismatch remain terminal stale outcomes. It SHALL persist bounded evidence identifying the source issue, criterion, source PR, merged SHA, recipe version, environment, command result, artifacts, and terminal outcome. The persisted environment SHALL retain the provisioned container identity and host after cleanup clears active resource references, and the closeout receipt SHALL include the final cleanup verdict, including cancellation. A missing run row during identity refresh SHALL NOT skip in-memory MCP or tool-sidecar and environment cleanup or attempt run-bound reference, ledger, log, or evidence writes; every run-bound log write SHALL also tolerate concurrent deletion so it cannot interrupt command execution or resource teardown. The claim SHALL atomically move exactly one delivery from queued to running, so a duplicate delivery SHALL not reclaim a running attempt and a replay SHALL not execute a terminal attempt, and unavailable, cancelled, stale, timeout, setup, and cleanup outcomes SHALL remain distinguishable from a pass.
  *Test:* `spec/jobs/closeout_verification_job_spec.rb`, `spec/services/technical_prerequisites/validate_execution_spec.rb`, `spec/services/containers/provision_spec.rb`.

- [x] **STAGED-CLOSEOUT-ADOPTION-012** — When an authorized trusted environment signal identifies a target revision, Paid SHALL automatically admit each eligible reviewed `live_environment` mapping into the closeout-verification lifecycle, deduplicated by issue, criterion, check version, environment class, and target revision; duplicate delivery and bounded reconciliation SHALL converge. Immediately before collection it SHALL recheck the signal and mapping, run only the allowlisted trusted measurement, attach the attempt and bounded result to the matching run, and submit current terminal evidence to the bounded audit path. A merge alone, an absent or stale signal, an unavailable or failed check, or a tenant or authorization mismatch SHALL not attest a criterion or unrelated criteria.
  *Test:* `spec/services/closeout_verifications/admit_live_target_spec.rb`, `spec/jobs/closeout_verification_job_live_target_spec.rb`, `spec/jobs/live_target_closeout_verification_sweep_job_spec.rb`.

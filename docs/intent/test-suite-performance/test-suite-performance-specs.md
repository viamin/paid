# EARS Specs: Test Suite Performance

- [x] **TEST-SUITE-001** — When CI partitions the non-system RSpec suite, it SHALL assign every eligible spec file to exactly one deterministic shard and SHALL exclude system and performance specs from that partition.
- [x] **TEST-SUITE-002** — When a shard count or index is invalid, the shard runner SHALL fail before executing tests; an empty selected shard SHALL fail rather than silently pass.
- [x] **TEST-SUITE-003** — When CI runs five test shards, each shard SHALL execute with isolated database/services/workspace state and SHALL preserve existing RSpec example execution and randomization.
- [x] **TEST-SUITE-004** — When CI checks combined coverage, it SHALL require one distinct non-empty report for every expected shard and SHALL reject missing, duplicate, malformed or unexpected reports.
- [x] **TEST-SUITE-005** — When CI collates complete shard reports, the final test check SHALL apply the existing Rails coverage filters and SHALL fail below 80% combined coverage; individually incomplete coverage SHALL not be mistaken for incomplete aggregate coverage.
- [x] **TEST-SUITE-006** — When any CI test shard fails or is cancelled, the stable final test check SHALL fail; system tests and the query-performance slice SHALL retain their existing execution coverage.
- [x] **TEST-SUITE-007** — When certificate behavior specs generate keys, they SHALL use the existing explicit smaller test-key option without changing production defaults or omitting signing, chain validation or encryption assertions.
- [x] **TEST-SUITE-008** — When Apple worker CLI specs run without DATABASE_URL, they SHALL inherit the configured Rails test connection rather than fail solely because a URL is absent.
- [x] **TEST-SUITE-009** — When CI profiles the test suite, it SHALL retain per-example timing artifacts and SHALL give the opt-in full-suite profiler a timeout sufficient for the known serial suite duration.

- [x] **TEST-SUITE-010** — When CLI commands only list providers, show usage, or reject invalid smoke arguments, they SHALL finish without booting Rails, preserve documented output and exit codes, and use the same provider catalog as application runner configuration.
- [x] **TEST-SUITE-011** — When hotspot specs reuse a persisted fixture graph, each example SHALL receive fresh model instances and transactional isolation; mutations SHALL NOT leak between examples and normal callbacks, validations and tenant constraints SHALL remain enabled.
- [x] **TEST-SUITE-012** — When prompt seed specs run, they SHALL load the actual default seed script once per group, isolate per-example mutations, and verify repeated synchronization preserves prompt and version identities.
- [x] **TEST-SUITE-013** — When PR scanner specs reuse their baseline project, they SHALL create its graph once per group with the existing scanner settings, refetch model instances per example, and roll back scenario-specific changes without SQL snapshot replay.
- [x] **TEST-SUITE-014** — When Apple live-validation specs exercise a focused scenario, they SHALL limit provisioning, recovery and diagnostics work to the scenarios under test and retain a full default-matrix integration check, including repeat counts and recovery convergence.
- [x] **TEST-SUITE-015** — When shell-tool availability specs run, they SHALL use manifest metadata without initializing a filesystem workspace; execution specs SHALL retain real shell execution, authorization and path-boundary checks.
- [x] **TEST-SUITE-016** — When HTTP retry specs suppress elapsed waiting, they SHALL replace only the external middleware timer, retaining actual attempts, configured backoff, retry exhaustion and mutation non-retry checks.
- [x] **TEST-SUITE-017** — When factory profiling identifies repeated stable setup, hotspot specs SHALL reuse only configuration graphs with fresh instances per example and transactional rollback; scenario runs, issues and authorization changes SHALL remain isolated, including distinct runs and issues for each simulated host slot.
- [x] **TEST-SUITE-018** — When a CI test-shard matrix leg is never created by the platform, CI SHALL classify that leg as recoverable (distinct from a leg that ran and failed), re-run exactly the recoverable legs with the same isolation and upload contract as the matrix, and the stable final test check SHALL fail when a ran leg failed, the classification cannot be established, a re-run leg fails, or any expected shard report remains missing.
- [x] **TEST-SUITE-019** — When the GitHub-hosted PostgreSQL service returns the known empty-result `cmd_tuples` adapter failure during system specs, or a complete system-suite attempt stalls for 80 minutes, CI SHALL restart and await the service container identified by GitHub Actions' job-service context before retrying the complete system suite for at most three total attempts; a missing or unavailable service container, any other failure, or exhaustion of those attempts SHALL fail the job without skipping examples.
- [x] **TEST-SUITE-020** — When GitHub-hosted test shards or dropped-shard recovery run, CI SHALL allow each full shard execution path 360 minutes to tolerate hosted-runner contention and bounded dependency retries, and a shard that reaches that bounded job timeout SHALL remain cancelled and fail the stable final test check.
- [x] **TEST-SUITE-021** — When GitHub schedules system-test workflow runs for the same pull request, CI SHALL NOT place them in a workflow concurrency group, because GitHub cancels superseded pending runs within a group and a cancelled required check cannot satisfy the pull-request gate.
- [x] **TEST-SUITE-022** — When GitHub-hosted system specs run, CI SHALL allow the system-test job GitHub's six-hour maximum so the browser suite can complete after bounded setup, and reaching that job boundary SHALL remain cancelled rather than being represented as a passing check.
- [x] **TEST-SUITE-023** — When JavaScript dependency setup transiently fails or times out in a test shard or dropped-shard recovery, CI SHALL retry the complete setup at most five times with each attempt bounded to twenty minutes, terminate only its owned process group, and reap its session leader before retrying, escalating after a finite grace period for TERM-resistant descendants. The watchdog SHALL own its timer and grace descendants in a separate session, acknowledge that session before cleanup targets its process group, and retain its exact owned PID until that acknowledgement so cancellation can terminate and reap it while readiness is pending. Setup-leader supervision SHALL permit TERM or INT cleanup while the leader remains live. Retry-backoff and termination-escalation timers SHALL be owned, terminated, and reaped before the wrapper returns on success, failure, timeout, or TERM/INT cancellation; cancellation SHALL not start another attempt or post-install step. Exhaustion SHALL fail the job without skipping setup, and the existing 360-minute job boundary SHALL remain authoritative.
- [x] **TEST-SUITE-024** — When a test shard or dropped-shard recovery installs ast-grep from its GitHub release archive, CI SHALL bound each transfer's connection and total duration, retain finite retry and pinned SHA-256 verification, terminate and reap the timed-out attempt's process group before retrying, and fail the job when installation remains unavailable rather than skipping structural-search coverage.
- [x] **TEST-SUITE-025** — When a pull-request CI workflow is cancelled or superseded while dropped-shard recovery is eligible or running, CI SHALL prevent recovery, dependency retry, and recovered test attempts from starting after cancellation, preserve bounded truthful artifact bookkeeping for work already completed, and retain a cancelled recovery as a failing result for the final coverage gate.
- [x] **TEST-SUITE-026** — When CI receives a trusted change that adds, removes, renames, or changes the write classification of an MCP tool, it SHALL run the complete Registry write-inventory and read-only-definition contract in a bounded preflight job before starting an expensive test shard; a failed preflight SHALL leave dependent shards skipped, SHALL fail the stable final test check, and SHALL record its elapsed time. When CI intentionally skips the preflight for an untrusted pull request, it SHALL also skip the stable final test check.
- [x] **TEST-SUITE-027** — When normal RSpec queries use the default PostgreSQL test connection, it SHALL enable prepared statements and preserve tenant visibility when the same prepared query, including a cached generic plan, runs across account changes; repeated closeout-candidate lookups SHALL remain eligible for prepared statements and preserve tenant visibility with a cached generic plan; schema-mutating specs SHALL preserve valid statement and schema caches without disabling prepared statements for unrelated examples.
- [x] **TEST-SUITE-028** — When tests boot without an explicit log level, the logger SHALL retain application info, warnings, and errors while omitting SQL debug output; when `RAILS_LOG_LEVEL=debug` is set, the logger SHALL emit SQL debug output while executing the same queries and preserving callbacks, tenant checks, and coverage.

- [x] **TEST-SUITE-029** — When the runner startup-budget regression asserts an exact remaining run budget, it SHALL freeze the scenario's wall clock and restore it afterward, preserving exact execution and startup timeout expectations and the application budget calculation.

- [x] **TEST-SUITE-030** — When an assignment-update spec checks a later explicit variant override, it SHALL start with a different explicit variant, verify both persisted states, and retain the existing assignment record so the update path is exercised independently of randomized selection.
- [x] **TEST-SUITE-031** — When agent-execution specs exercise pure runner naming, fallback ordering, attempt counting or harness-command construction, they SHALL retain their scenario assertions without constructing persisted factory graphs; execution scenarios SHALL retain their run lookup, container reconnect and scenario-specific persistence checks.
